# 决策记录：暂不引入 CodeMirror 6（编辑器核心）

日期：2026-11-09　状态：**已决定，不引入**

## 结论

继续用「`<textarea>` + 同字体覆盖层」方案。不引入 CM6。

## 实测数据（决定依据）

**CM6 最小组合**（state + view + commands + language + lang-markdown + lezer/highlight + 行号 + history + 默认高亮）：

```
esbuild --bundle --minify  →  500 KB
gzip -9                    →  175 KB
```

**可被替换掉的现有代码**：

| 部分 | 行数 |
|---|---|
| 覆盖层高亮（`renderEditorHighlight` 等） | 22 |
| 行号槽（`updateGutter` 等） | 10 |
| Vim 自研实现 | 79 |
| 光标/行偏移换算 | 9 |
| **合计** | **~110 行** |

即：删 110 行，换 +500 KB。

**耦合面（真正的成本）**：

```
editor.value 直接读写   110 处
selectionStart/End       66 处
scrollTop 同步           17 处
```

CM6 没有 `.value`（读 `state.doc.toString()`，写 `dispatch({changes})`），选区是 `EditorSelection`。
176 个读写点要逐个重写，且各自带着假设：

- 自研 `undoStack`/`redoStack` 与 CM6 `history()` 冲突，必须二选一
- 表格 Tab 跳格要改成 keymap 拦截
- 搜索命中高亮依赖覆盖层的 HTML 字符串，要改成 Decoration
- Vim 块光标是独立 DOM 元素定位，要接 `@replit/codemirror-vim`（额外体积）或放弃

## 不做的理由

1. **净收益不足**：主要收益是「移动端也有高亮」和「超大文档滚动更顺」，两者都不是当前主场景。
2. **代价是一次编辑器层重写**（176 个耦合点 + 撤销/Vim/表格/搜索四处专门适配），估算 6–8 个工作日。
3. **打破零构建**：CM6 必须打包，产物进 `vendor/` 可行，但升级时要重跑构建。

## 两个被纠正的说法（留档，避免以后再被同类分析带偏）

- ❌「CM6 体积比手写的光标坐标计算更小」→ 手写部分几 KB，CM6 是 500 KB。
- ❌「DPI 125%/150% 必然错位」→ 覆盖层与 textarea 用同一字体/字号/行高，实测字宽完全一致；
  真正风险是 IME 组合期与 CJK 字体回退，不是「必然错位」。

## 重新评估的触发条件

只有满足其一才重新考虑：

1. 主要写作场景转移到手机
2. 文档经常超过 2 万字且滚动明显卡顿

满足时先做**半天 POC**，只验证三件事，任一不过就放弃：

- 3000 字中文 + DPI 150% 下光标与文字对齐
- 中文输入法组合期（拼音未上屏）正常
- 首屏体积与加载时间（懒加载后）

## 替代的下一步

比 CM6 性价比高得多的小改动：`sw.js` 加 **Navigation Preload**（半小时，解决网络优先策略下 SW 启动慢的首屏卡顿）。
