## 一、踩到的第一个坑：同步护栏拦不住 ReDoS

最初我给正则加了「循环里检查时间预算」的护栏，然后写了个灾难性回溯的测试：

```js
Core.safeMatchCount('a'.repeat(4000), /a+a+a+a+a+a+a+a+a+a+b/, { budgetMs: 30 })
```

**测试直接挂死 30 秒**。原因很直白：灾难性回溯发生在**单次 `exec()` 内部**，JS 无法在执行中途打断，所以「循环里查预算」只能拦住「匹配次数极多」，拦不住「一次匹配就爆炸」。

修正方案（最终采用）：

1. `lib/md-core.js` 里保留 `safeMatchCount`（拦住「次数爆炸」那类），并在注释里**明确写清能力边界**；
2. 真正的兜底是 `lib/md-regex-worker.js`：正则任务丢进 Worker，主线程 3s 硬超时 → `worker.terminate()`；
3. Worker 里跑的逻辑本体仍是 `md-core.runRegexJob()`（纯函数），所以**Worker 里的逻辑也被 node --test 覆盖**；
4. 同步路径仅在 Worker 不可用时降级，且此时长度上限 200 字符。

E2E 断言：输入 3000 个 `a` + 11 个 `a+` + `b` 的正则，页面在 4 秒内给出「已中断」提示，并且主线程同步循环仍能在 2s 内跑完（证明没被卡住）。

## 二、存储层：一次写入不该牵动 4MB

### 2.1 改前的问题

```
writebackLib()  ──> idbGet(doc)            // 读出正文 + 20 条历史快照（最大 200KB × 20）
                ──> idbPut({...history})   // 全部写回
saveReadingProgress() ──> idbGet() + idbPut()   // 只为存一个 scrollRatio 浮点数
saveDraft()     ──> localStorage.setItem(整篇)   // 每 800ms 同步写，且与文库内容重复
```

滚动停一下就是一次「读出几 MB → 写回几 MB」。

### 2.2 改后的分层（DB v3）

| 仓库 | keyPath | 内容 | 写入时机 |
|---|---|---|---|
| `docs` | `id` | 元信息 + 正文 | 编辑去抖 800ms / pagehide |
| `images` | `id` | 图片 Blob | 粘贴/拖拽图片 |
| `history` | `hid` = `docId@时间戳`（+`byDoc` 索引） | 版本快照 | 满足 `shouldSnapshot` 时 |
| `positions` | `id` | `{scrollRatio, lastReadAt}` | 滚动停 2s |
| `drafts` | `id` | 大文档草稿（>1MB） | 编辑去抖 800ms |

**升级策略刻意做成「只新建仓库，不破坏性迁移」**：旧数据里的 `doc.history` 由 `readHistory()` 兜底读出，并在下一次回写时自然淡出。理由是这个库是用户的真实笔记，宁可多一段兼容代码，也不要写一个可能吃掉数据的迁移块。

### 2.3 历史快照策略（`md-core.shouldSnapshot`）

```js
if (!lastAt) return true;                                  // 首版必存
if (now - lastAt >= 5 * 60 * 1000) return true;            // 距上次 ≥5 分钟
return |newLen - prevLen| / prevLen >= 0.05;               // 或长度变化 ≥5%
```

旧策略下，「写下第 21 段文字」就把最早的版本挤掉了——20 条快照全是最近几分钟的近似副本。现在快照真正覆盖「不同阶段」。

E2E 断言：连续 6 次编辑（每次间隔 900ms）后，`history` 仓库条目 ≤ 3。

## 三、撤销栈：程序化改写不该杀掉 Ctrl+Z

`editor.value = next` 会清空浏览器原生 undo 记录。旧代码只在 Vim 里用 `document.execCommand('undo')` 打了补丁，格式刷 / 全部替换 / AI 应用之后按 `Ctrl+Z` 完全无反应。

做法（不改动原生输入体验）：

- 只对「程序化改写」压快照：`commitText` / `insertAtCursor` / 历史版本恢复 / Vim 降级路径；
- `Ctrl+Z` 仅在 **我们自己的栈非空** 且焦点在编辑器/页面本体时接管，否则放行浏览器原生 undo；
- 上限 60 步 + 8MB 总量，按最旧丢弃；
- 切换文档（打开文件 / 打开文库文档 / 新建）时 `resetUndo()`。

## 四、可访问性：用观察者，而不是改 12 个调用点

12 个弹窗都是通过 `el.hidden = false` 打开的。与其在每个调用点插一行 a11y 代码，不如**观察 `hidden` 属性**：

```js
new MutationObserver(() => { ... onModalOpen(m) / onModalClose(m) ... })
  .observe(m, { attributes: true, attributeFilter: ['hidden'] });
```

打开时：入栈 → 背景 `.app` 设 `inert` → 焦点移入第一个可聚焦元素。
关闭时：出栈 → 解除 `inert` → 焦点归还给打开前的元素。
Tab：在栈顶弹窗内循环。
Esc：只点「取消/关闭」按钮，**绝不强行 `hidden = true`**——否则 `askConfirm` / `askInput` 的 Promise 会永远挂起（这是我在写第一版时踩的坑，被 E2E 抓到了）。

另外补了菜单 `role="menu"` 的方向键 / Home / End 导航，以及 `prefers-reduced-motion` 与 `:focus-visible`。

## 五、备份：用户的笔记不该只有一份

文库只存在浏览器的 IndexedDB 里，清站点数据即全丢；NAS 同步要手动配凭据且是可选功能。

于是自己写 ZIP（`md-core.zipStore` / `unzipStore`，约 120 行）：
- 写：store 模式（不压缩），UTF-8 文件名标志位，CRC32 自算；
- 读：支持 store + deflate（`DecompressionStream('deflate-raw')`），能从系统压缩工具产出的 zip 导入；
- 单测覆盖：文本 + 中文文件名 + 二进制往返、空 zip、非法输入、CRC32 已知向量。

导出内容：`manifest.json` + `docs/<id>.md` + `docs/<id>.json`（元信息 + 快照摘要）+ `images/<id>`。

## 七、这次**没做**的，以及为什么

| 项 | 原因 |
|---|---|
| 把 `app.js` 拆成 ES modules | 5644 行 + 239 个函数的整体迁移，回归面覆盖不了；先把纯逻辑下沉 + 补测试，才是低风险的第一步 |
| 内联事件换成 `addEventListener` 以支持 CSP | 39 处内联 `onclick/onsubmit` + 内联 `<script>`，改完才能上 CSP；目前没有 XSS 证据（DOMPurify + escapeHtml 用法正确），属「有第二道防线」的长期工作 |
| 预览按块增量渲染 | 收益大但风险高（mermaid/KaTeX/图片解析都挂在全量重渲染链上）。这次先做了「内容未变则跳过渲染」+ 统计节流 + 行偏移缓存这些无损优化 |
| `highlight.js` 换 common 子集 | 需要重新构建 vendor 包（引入构建步骤），与「零构建」冲突 |
| docs 表拆 meta/content 两表 | 拆分后全文搜索仍要读全部正文，收益不如先把 history 拆出去明显；已保留为后续项 |
| 本地存储 key 统一命名空间 | 27 个 key 的读写散落各处，重构面的收益低于风险，留待模块化时一并处理 |
