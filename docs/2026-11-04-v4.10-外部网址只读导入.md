# v4.10 从网址打开（只读）——实现与安全性分析

> 日期：2026-11-04  
> 版本：v4.10  
> 一句话：**贴一个 https 链接，把里面的 Markdown 排版读出来；只读，绝不留痕。**

---

## 一、为什么要做，以及为什么不能"直接 fetch"

需求很小：看到一个 `.md` 的网址，想用 mdviewer 读，而不是看浏览器的纯文本。

但浏览器不允许。`fetch('https://别的站/x.md')` 属于跨域读取，除目标站主动回 `Access-Control-Allow-Origin`，否则一律被拦。mdviewer 是部署在 GitHub Pages 上的纯静态 PWA（`md.want.biz`），没有任何服务端，所以**只能借一个代收点**。

方案定了两个：

| 场景 | 代收点 | 说明 |
|---|---|---|
| 同源/LAN（`serve-web.js` 提供的 `/mdviewer/`） | `GET /__fetch?url=` | 同源，零 CORS 麻烦 |
| GitHub Pages（公网纯静态） | `GET https://share.want.biz/fetch-md?url=` | Cloudflare Worker，**默认关闭**，需显式开启 |

前端自动选路（`resolveFetchProxy()`）：主机名是 `md.want.biz` 或 `*.github.io`，或用 `file:` 打开 → 走 Worker；其余走同源 `/__fetch`。

**关键认知**：代收点等于「别人能指挥我们的服务器去访问任意地址」。不设防就是一台公开 SSRF 机器 + 免费反代。所以这个功能的重心不在"能不能取到"，而在"绝不去取我们不该碰的地方"。

## 二、一次取文的完整链路

```
用户：⋯ → 🌐 从网址打开（只读）  →  输入 https://raw.githubusercontent.com/…/README.md
   │
   ├─① 前端预检          lib/fetch-guard.js  checkFetchUrl()     不合规立刻中文提示，不发请求
   │
   ├─② 请求代收点        GET /__fetch?url=<encoded>   （credentials: omit，带 X-Mdviewer: 1）
   │     ├─ 限流        每 IP 每分钟 30 次（超了 429）
   │     ├─ 开关        SERVE_FETCH=0 或 guard 文件缺失 → 501（fail closed）
   │     ├─ 复查        同一个 checkFetchUrl() 再跑一遍（前端那次只是 UX）
   │     ├─ 取           redirect:'manual' / credentials omit / referrerPolicy:no-referrer / 10s 超时
   │     ├─ 逐跳复查     每一跳 Location 都过 checkRedirect()（相对地址按基准解析后复查）
   │     ├─ 限体积       边读边数，超 2MB 立即 cancel() → 413（不信 Content-Length）
   │     ├─ 限类型       text/markdown · text/x-markdown · application/markdown · text/plain · octet-stream
   │     │               text/html 单独归类 → 415「这是网页不是 Markdown」
   │     └─ 限内容       looksLikeText()：魔数 + NUL + 控制字符比例 → 二进制直接 415
   │
   ├─③ 前端二次量体积    arrayBuffer.byteLength > 2MB → 拒绝（防代收点被换掉）
   │
   ├─④ 进只读模式        currentLibId / currentShareId / currentFileHandle 全部置 null
   │     ├─ editor.readOnly = true，body.remote-mode，顶部横幅显示来源主机
   │     ├─ afterChange({skipWriteback:true})；writeDraftNow() 见到 remoteOrigin 直接 return
   │     └─ setView('preview')：来看的，不是来写的
   │
   ├─⑤ 渲染              marked → REMOTE_SANITIZE（宽禁档）→ 外链 hook → 图片延迟加载
   │     └─ 跳过 renderAudioPlayers / renderImageEmbeds / mermaid
   │
   └─⑥ 退出              「退出」按钮 = location.assign(origin+pathname)，远程正文从未落盘，丢了也没损失
```

## 三、为什么安全（逐层拆）

写这份分析的目的是让后来的人能判断"某条规则能不能放宽"。每条规则都对应一种真实滥用方式，只看代码看不出取舍理由。

### L0 前提：先承认代收点是攻击面

代收点对外暴露的接口是「给我一个 URL，我去取」。攻击者拿到它能做什么：

1. **探内网**：`url=http://169.254.169.254/latest/meta-data/iam/...` 读云元数据拿临时凭据；`http://10.0.0.5:8080/admin` 摸内网服务。
2. **当反代跳板**：大量请求经由我们的出口 IP，干被封禁的事，封的是我们的域名。
3. **回连 / 打内网 Web 漏洞**：GET 一个带参数的内部接口就能触发副作用（很多内部管理接口是 GET 就能改状态的）。
4. **消耗资源**：慢速响应拖住并发、超大文件打满内存。

所以规则不是"尽量挡"，而是**白名单式放行 + 默认拒绝**。

### L1 目标检查（`checkFetchUrl`）

| 规则 | 挡的攻击 | 为什么不能更宽松 |
|---|---|---|
| 只 `https:` | 明文嗅探、`file://` 读本机文件、`data:`/`javascript:` 注入 | `http://` 对我们没有任何必要性（文档托管都有 https） |
| 拒绝任何 IP 字面量（v4/v6） | `169.254.169.254` 云元数据、`127.0.0.1` 本机、`10./172.16./192.168.` 内网 | 若改成"按网段判断"，就得枚举 CGNAT(100.64/10)、保留段、IPv6 ULA…**漏一段就是事故**。宁可拒绝 `https://1.1.1.1/x.md` 这种极少数合法用法 |
| 拒绝单段主机名（`localhost`、`intranet`、`myrouter`） | 内网 DNS 里的短名 | 公网文档托管一定是 FQDN |
| 拒绝 `.local/.internal/.lan/.home.arpa/.corp/…` 后缀 | mDNS 局域网设备、企业内网域名 | 这些保留域不可能承载你要读的文章 |
| 拒绝 `user:pass@host` | 钓鱼（把密码写进 URL）、凭据被写进日志 | 没人用这种方式托管公开文档 |
| 只允许 443 端口 | 打内网非标端口上的服务（Redis 6379、管理后台 8080…） | 443 已覆盖 99.9% 的文档站 |
| 跳转逐跳复查（`checkRedirect`） | `https://evil.com → http://169.254.169.254/` 绕过；`→ file:`；`→ localhost` | **不能只做"同域限制"**——攻击者可以在自己域名下 302 到内网，同域限制形同虚设。真正的防线是"跳转后的地址从零复查，不继承上一跳的信任" |

### L2 传输执行

| 措施 | 挡的攻击 |
|---|---|
| `redirect: 'manual'` | 让浏览器/undici 自动跟跳转会绕过 L1（自动跳转发生在你能看一眼之前） |
| `credentials: 'omit'`，不发 Cookie/Authorization，`referrerPolicy: no-referrer` | 不把我们的任何凭据/来源信息带给对方；也不会因为带了 cookie 而被当成已登录用户 |
| 10 秒 `AbortController` 超时 | 慢速攻击拖住 worker/进程；对端挂住连接导致并发耗尽 |
| **边读边数**，超 2MB 立刻 `reader.cancel()` | `Content-Length: 5` 实际发 5GB；chunked 响应没有长度；zip bomb 类放大 |
| Content-Type 白名单（且 `text/html` 单独归类） | 把代收点当通用 HTML/JSON 反代；也避免"取回一个网页"这种无意义行为 |
| `looksLikeText()`（魔数 + NUL + 控制符比例） | 把 zip/png/pdf 当 md 塞进渲染管线（`application/octet-stream` 的兜底就是靠它） |
| 每 IP 30 次/分钟（serve-web 内存计数；Worker 可选 KV） | 被当免费反代批量刷；Worker 侧还要求在 Cloudflare 面板配 WAF 限流，**因为 Workers 免费版没有内置限流** |
| 日志只记 hostname + 字节数 | 取文 URL 的 query 里可能带私有 token，落日志等于泄露 |
| CORS 只回白名单 Origin（不回 `*`） | 任意网站用 JS 借我们的代收点 |
| 开关式启用（Worker 默认关；serve-web `SERVE_FETCH=0` 可关） | 出事能一键止血，不用改代码 |

### L3 内容渲染（这一次的最关键改动）

原来的消毒配置是给**自家**文档用的：

```js
DOMPurify.sanitize(html, { ADD_TAGS: ['audio','source'], ADD_ATTR: ['controls','preload','autoplay','loop'] })
```

对别人的文档，这套配置有三个真实漏洞：

1. **`autoplay`** —— 一行 `<audio autoplay src=…>` 就能"一打开就出声"，也能当信标（请求发出=你打开了）。
2. **远程图片自动加载** —— 最阴的一种。`![](http://10.0.0.10:8080/admin)` 会在**你的内网里**发一个请求：既能探你的 LAN 服务（响应看不见，但请求出去了），又能当跟踪像素（对方知道你何时读了文、你的出口 IP）。这是被动泄露，不给任何提示。
3. **外链无 `rel`** —— 点击同标签跳走，当前未保存内容丢失；以及反向 tabnabbing。

现在外部内容走 `REMOTE_SANITIZE`（宽禁档）：

| 措施 | 挡的攻击 |
|---|---|
| `FORBID_TAGS`：`style/link/meta/base/form/input/button/select/textarea/iframe/object/embed/audio/video/source/track/noscript` | 自动发请求的一类（`link` 预加载、`iframe`、`object`）、可执行的一类（`iframe srcdoc`、`embed`）、表单钓鱼、样式覆盖 UI（假登录框） |
| `FORBID_ATTR`：`autoplay/srcset/ping/formaction/id/data-libimg` | `ping` 点击上报、`srcset` 绕过单地址检查、`id` 伪造锚点、`data-libimg` 让你自己的文库图片出现在别人的文档里 |
| `ALLOW_DATA_ATTR: false` | `data-*` 被自家代码误读 |
| `ALLOWED_URI_REGEXP`：只放 `http:`/`https:`/`mailto:`/`#`/`data:image/(png\|jpe?g\|gif\|webp);` | `javascript:` 链接、`data:text/html` 新窗口 XSS |
| hook：`<a>` 强制 `target=_blank` + `rel="noopener noreferrer nofollow"` | 反向 tabnabbing、Referer 泄露、被搜索引擎当外链背书 |
| hook：外链 `<img>` → `data-remote-src` + 1×1 占位，**点击才真加载** | 跟踪像素、内网探针、被动 IP 泄露。这是本次最重要的一条：**默认零请求** |
| hook：`<img referrerpolicy=no-referrer loading=lazy>` | 同上 |
| hook：`style` 里含 `url(`/`expression(`/`@import` 就整个删掉 | `style="background:url(http://…)"` 又是一次探针 |
| 跳过 `renderAudioPlayers()` / `renderImageEmbeds()` | 这两步是**消毒之后**的 DOM 加工，会把裸链接变成 `<audio>`/`<img>`——外部内容直接不给这个能力 |
| 跳过 mermaid | 图定义是"可执行描述语言"，渲染成 SVG 属于额外攻击面；读别人的文章不需要流程图 |

**没跳过的：KaTeX。** 理由：KaTeX 只产出文本级排版，`trust` 默认 `false`（`\href`、`\url` 这类命令不生效），输出是纯 `<span>` + 行内样式。行内样式里带 `url()` 的情况已被上面的 hook 兜掉。

### L4 状态隔离（防止"渲染安全但状态被污染"）

只把 HTML 洗干净是不够的。远程内容如果进了本地状态，就会在**你完全不知情的时候**回到你的可信上下文里。所以：

| 状态 | 处理 | 不做会怎样 |
|---|---|---|
| 草稿 `localStorage/md-draft` | `writeDraftNow()` 见 `remoteOrigin` 直接 return | 刷新后 `loadDraft()` 把它当"你的未完成稿"自动恢复；同时**覆盖掉你真正在写的草稿** |
| 文库回写 | `currentLibId = null` + `skipWriteback` | 别人的内容被写进你的文库，甚至参与 NAS 同步 |
| 协作分享 `currentShareId` | 置 `null` | 拿别人的文档**覆盖掉某个协作链接**的内容 |
| 本地文件 handle | 置 `null` | Ctrl+S 把别人的文档写回你上次打开的那个 `.md` |
| 分享/发布/上传/转播客 | `blockInRemoteMode()` 一处处显式拦 | 一键把别人的文章发到你的博客/NAS/IMA |
| 编辑 | `editor.readOnly = true` | 用户以为在改自己的稿子；而且一改就会触发各种写入路径 |
| 退出 | 直接 `location.assign(干净地址)` | 远程正文本来就没落盘，重载不丢东西；比"清空编辑器"更彻底（内存里的引用也一起没了） |
| 唯一的口子 | 菜单「📚 添加到文库」→ 二次确认「认领」 | 用户确实想留一份时，明确转成"我的文档"，之后一切按普通文档处理（`adoptRemoteDoc()`） |

这一层的意义用一句话概括：**即使 L3 的消毒被绕过，最坏情况也只是"这一页显示乱了"；没有持久化，恶意内容不会在你下次打开时自动回来。**

### L5 能力降级（fail closed，而不是 fail open）

| 条件 | 行为 | 若反过来（fail open） |
|---|---|---|
| `lib/fetch-guard.js` 没加载到（缓存不完整） | serve-web：`/__fetch` 返回 501；前端：不取文 | 裸奔的取文端点 |
| 代理找不到 guard 文件 | 同上 501（连"自己写一套弱检查"都不做） | 规则漂移，代理和前端各一份判断 |
| `DOMPurify` 没加载 | 外部内容**不渲染**，只给提示 | 把未消毒的 HTML 直接 `innerHTML` |
| 取文失败（超时/被拦/网络不通） | toast 中文原因，并**回落到普通启动**（文库/草稿） | 用户卡在空白页 |

## 四、残余风险（诚实清单）

写清楚，避免误以为"已经万无一失"：

1. **DOMPurify / marked 自身的 0day**。当前 DOMPurify 3.4.12。若消毒器本身被绕过，且绕过方式能执行脚本，则页面上下文里的 `localStorage`（含 `nas-auth`、`md-ai-config`）可被读取。缓解：L4 保证不持久化，关掉标签页即结束；要更强可上 sandbox iframe（见六）。
2. **代收点被当免费反代**。L1/L2 让它只能取"公开的 https 文本"，但仍能用来：借我们的出口 IP 刷别人的站、拿对方 404/200 判断某个 URL 是否存在。Worker 侧必须配 WAF 限流；serve-web 侧已有内存限流，且只在 LAN/WireGuard 内可达。（**现状：Worker 已上线但尚未配 WAF/KV 限流，属已知待办。**）
3. **点开远程图片之后**，请求确实发出了——对方能看到你的出口 IP 和时机。这是用户主动行为，只能靠"默认不加载 + 标题提示"来控制。
4. **`?url=` 自动加载**。别人发你一条 `https://md.want.biz/?url=…` 的链接，你点开就会渲染那篇内容（横幅会显示来源主机）。若你担心这一点，可以改成"参数不自动加载、需要再点一次确认"。
5. **用户主动"存入文库"之后**，内容即视为可信（可编辑、会回写、会同步）。这是设计选择：认领是显式动作。
6. **不覆盖的范围**：浏览器扩展、其他标签页、DNS 层面的攻击、目标站的 TLS 被攻破。这些不在应用层能管的范围内。

## 六、已知取舍与后续

| 取舍 | 原因 | 要改的话 |
|---|---|---|
| 不支持 `http://` | 公开文档都有 https；http 会把内容与来源暴露在链路上 | 明确反对 |
| 不支持 IP 字面量 | 不做网段枚举就不会漏判 | 明确反对 |
| 远程文档不渲染 mermaid / 不显示音频 | 两者都是额外攻击面 | 若确实需要，mermaid 必须以 `securityLevel:'strict'` + `htmlLabels:false` 且只在「信任此来源」后开启 |
| 图片默认不加载 | 零被动请求是最强的一档 | 已提供点击加载；可按来源做白名单 |
| GitHub Pages 版依赖 Worker | 纯静态无服务端 | 部署步骤见下 |
| 没有 sandbox iframe | 成本 vs 收益：加了之后 mermaid/公式/目录/同步滚动全部要重做 | 若要开放给"不完全信任的人发来的链接"，就值得上：`<iframe sandbox="allow-popups" srcdoc=…>` + srcdoc 内嵌 `<meta CSP content="default-src 'none'; style-src 'unsafe-inline'; img-src data:">` |

guard 查找顺序（`SERVE_FETCH_GUARD` → 同目录 → `mdviewer/lib/` → `/root/mdviewer/lib/` → `/workspace/ops/`），**一个都找不到就关掉端点**。所以换机器部署时，记得把 `fetch-guard.js` 一起带过去，或设 `SERVE_FETCH_GUARD`。

环境变量：

| 变量 | 默认 | 作用 |
|---|---|---|
| `SERVE_FETCH` | 开 | 设为 `0` 关闭 `/__fetch` |
| `SERVE_FETCH_ORIGINS` | 空（仅同源） | CORS 白名单，逗号分隔，如 `https://md.want.biz` |
| `SERVE_FETCH_RATE` | 30 | 每 IP 每分钟次数 |
| `SERVE_FETCH_GUARD` | — | 指定 guard 文件路径 |

> 注意：`serve-web.js` 的 `/__fetch` 一旦开在 `0.0.0.0:8080`，**能访问这个端口的人都能用它取文**。它只在内网/WireGuard 内可达算合理；若要更严，加 `SERVE_PASS`（Basic 认证）——前端 `fetchRemoteText()` 走同源时浏览器会自动带上已认证的会话。

**限流：实测走过的三个坑（2026-11-05）**

原本打算「建个 KV 当计数器」，实测发现**KV 做不了这件事**，最后用 Durable Object 解决：

| 方案 | 实测结果 | 为什么不行 / 为什么行 |
|---|---|---|
| KV 计数 | 连打 70 次，**0 次 429**；KV 里只有 2 个 `rl:<ip>` 键、计数不增长 | ① KV 的 `get()` 在边缘有最长 **60 秒读缓存**，突发期间读到的始终是旧值；② 同一个 key **每秒只允许 1 次写入**，连打时写直接失败 |
| isolate 内存计数 | 同样 0 次 429 | 低流量 worker 的 isolate **复用没有保证**，70 次连续请求分不到同一个 isolate，计数各自为政 |
| **Durable Object** | 连打 80 次 → **13 次 429**，`{"reason":"rate-limit","message":"请求过于频繁（30 次/分钟）"}`，静置 62 秒后自动恢复 | 按 IP 定位到**同一个 DO 实例**，请求串行执行、状态强一致 → 计数准确 |

三道闸的最终顺序（`src/worker.js`）：**DO（准确）→ isolate 内存（顺带）→ KV（只作事后观察）**。
任一道坏掉都不影响取文——可用性优先；拦下来的才会返回 429。

> 测试时注意：沙箱出口 IP 会在 `111.229.52.240` / `124.221.73.10` 之间轮换，
> 所以「每个 IP 30 次」意味着连打 60 次左右才开始出现 429，这是**语义正确**而不是没生效。
> 想更快看到效果就对单一 IP 打（或用 `cf-connecting-ip` 观察两边的计数）。

## 八、给后来者的一句话

这个功能看起来只是"读一个 URL"，实际动了四条线：**传输（代理）、解析（消毒档）、状态（归属隔离）、能力开关（fail closed）**。任何一条想走捷径，安全结论就不成立：

- 只做消毒、不做归属隔离 → 内容安全了，但它在下次打开时自己回来，且覆盖你的草稿；
- 只做目标检查、不做传输限制 → 能挡住内网，但挡不住 `Content-Length` 撒谎和慢速拖死；
- 只做前端检查、不在代理侧复查 → 前端只是 UX，绕过它太容易。

改动请先改 `tests/fetch-guard.test.js`，让规则变化留在 diff 里。
